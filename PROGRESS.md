## Phase 2 – Thu thập dữ liệu
- 2.1: `GitLabClient` (httpx): phân trang keyset (Link rel=next) + X-Next-Page, retry exponential + jitter cho 429/5xx/lỗi mạng (tôn trọng Retry-After), rate limit phía client (req/s) + chờ khi RateLimit-Remaining thấp, timeout 30s; fallback `/changes` khi `/diffs` 404. Test bằng respx.
- 2.2: `GitLabCollector` ghi raw_gitlab cho project, commits (+ diff, bỏ qua merge commit), MRs (+ commits/notes/diffs), pipelines (+ detail để có duration). Diff chỉ lưu thống kê theo file, KHÔNG lưu nội dung (quy tắc AGENTS: không lưu source) → Phase 3 lấy diff trực tiếp từ GitLab. - 2.3: extract (raw → dataclass, bản ghi raw sau thắng) + convert (upsert domain: commits, merge_requests, mr_commits, mr_notes, pipelines, accounts). LOC lọc theo IGNORE_PATHS; merge commit giữ `is_merge=true`. `first_review_at` = note không phải system và không của tác giả; `review_rounds` = số lần push (system note 'added N commits') sau ít nhất 1 note review. Commit chỉ có trong danh sách MR được chèn tối thiểu (không ghi đè). Chạy 2 lần không nhân đôi.
- 2.4: `sync_project` (collect → extract chỉ raw của lần chạy này → convert) trong 1 transaction; khoá `pg_try_advisory_xact_lock` để không sync trùng; `last_synced_at` chỉ tiến khi thành công. Scheduler enqueue `sync_project_job` cho mọi project mỗi SYNC_INTERVAL_MIN (job_id cố định, timeout 2h).
- 2.5: `POST /api/v1/webhooks/gitlab`: so X-Gitlab-Token constant-time với secret của mọi connection có project đó (secret không giải mã được → coi như sai, ghi log), chỉ nhận Push/MR (open, reopen, update, merge)/Pipeline, chống trùng bằng Redis SET NX theo X-Gitlab-Event-UUID (7 ngày), trả 200 rồi enqueue. Job: MR update có oldrev → đánh dấu review cũ `superseded`, rồi enqueue sync project. Enqueue review mới làm ở 3.5 khi có worker review.
- 2.6: autolink chạy cuối mỗi sync: gitlab_user ← public email GitLab hoặc username@ALLOWED_EMAIL_DOMAINS; git_email ← primary_email, email noreply GitLab (parse id), username@domain cho phép, public email GitLab; không ghi đè link có sẵn; bot (renovate, dependabot, *_bot, ci-bot…) → user active=false. Import CSV teams/users/accounts idempotent, lỗi báo theo file:dòng, import tay thắng autolink. `unmapped_accounts()` cho danh sách unmapped; API + trang admin làm ở 5.1/5.3 (cần RBAC), CLI ở 2.7.

## Phase 3 – AI Review
- 3.1: \`LLMProvider\` + \`ClaudeCodeProvider\` (gọi \`claude -p --output-format json --json-schema …\`, tắt mọi tool, không đọc settings/session, cwd thư mục tạm rỗng, diff qua stdin; timeout 120s, retry 3 lần, rate limit; token OAuth/API key qua biến môi trường, không lộ trong lỗi) + \`FakeLLMProvider\`. CLI không hỗ trợ \`temperature=0\` như spec 06 yêu cầu → chấp nhận, đo độ ổn định bằng eval (3.8). Dockerfile cài CLI bản cố định: chờ Docker Desktop (đang treo) để build thử.
- 3.2: lọc SENSITIVE_PATHS (không gửi LLM), IGNORE_PATHS, file xoá/quá lớn/binary; che secret bằng regex (token GitLab/GitHub/Anthropic/AWS/Slack, JWT, Bearer, private key, mật khẩu trong URL, \`password = "…"\`); diff kèm số dòng mới để LLM trích đúng dòng; chunk theo MAX_TOKENS_PER_CHUNK (file lớn tách theo hunk); context ±30 dòng gộp vùng chồng nhau, chỉ thêm khi còn chỗ.
- 3.3: prompt theo khung 06 + rubric v1 (`RUBRIC_VERSION`), schema Pydantic `LLMReview` (cũng là JSON schema gửi qua --json-schema), parser nhận structured output hoặc tách JSON từ text, sửa 1 lần nếu sai schema rồi bỏ. System prompt coi diff/context là dữ liệu không tin cậy (chống prompt injection). Finding viết bằng tiếng Việt như ví dụ trong 06.
- 3.4: hậu xử lý: bỏ finding confidence < MIN_CONFIDENCE, file không có trong diff, dòng ngoài mọi hunk; dòng context (không phải +) → hạ thành info; code_excerpt ≤ 40 dòng; fingerprint = sha256(file, category, code chuẩn hoá) không phụ thuộc số dòng; gộp trùng giữa các chunk giữ bản mạnh nhất.
- 3.5: `ReviewService` (lấy diff trực tiếp từ GitLab → prepare → chunk + context → LLM → hậu xử lý → điểm theo 08 kèm trần 50 khi có critical → lưu finding) + job RQ `review_mr_job`/`review_commit_job` (MR/commit chưa có hoặc head lệch → sync trước; đang sync → retry 60/120/300s). Webhook enqueue review khi MR open/reopen/update có commit mới, và khi push thẳng lên nhánh mặc định với commit không thuộc MR nào. Mỗi sha chỉ review 1 lần; review `running` quá 30 phút được nhận lại; review xong → review cũ của MR `superseded`. Project `allow_external_llm=false` → `skipped`. Bảng 03 không có cột `score_breakdown` nên điểm tham khảo của LLM không lưu.
- 3.6: lưu model/token/chi phí theo review (cộng cả lần sửa JSON); vượt MONTHLY_LLM_BUDGET_USD → review `failed` ("monthly LLM budget reached", chạy lại được) + log ERROR; từ 80% → log WARNING.
- 3.7: 1 comment tổng trên MR khi `post_mr_comment=true` (điểm, đếm theo severity, top 5), review lại thì sửa đúng comment đó (nhận diện bằng marker ẩn vì 03 không có cột note_id); lỗi GitLab không làm hỏng review.
- Docker Desktop treo do ổ C: đầy; theo yêu cầu người dùng, từ đây không kiểm bằng Docker trên máy: chạy lint/mypy/unit test tại chỗ, test tích hợp chạy trên GitHub Actions. Dockerfile đã thêm Claude Code CLI 2.1.308 nhưng **chưa build thử**.
- 3.8: bộ eval 20 case (5 security, 5 bug, 3 perf, 3 maintainability, 4 sạch) trong `tests/eval/cases` + `make eval` (`python -m app.review.eval`): precision/recall critical+high theo khớp file + dòng (±2), báo cáo JSON vào `tests/eval/results/` (gitignore). Harness được test bằng reviewer 'oracle' (=1.0) và reviewer im lặng (fail). Prompt thêm giải thích marker `***REDACTED***` để vẫn bắt được secret hard-code sau khi che. Sửa test tích hợp hỏng trên CI (route file raw chưa mock).

## Phase 4 – Chấm điểm & Tổng hợp
- 4.1: công thức review_score (08) đã có từ 3.5; thêm trọng số theo `rubric_version` (`WEIGHTS_BY_RUBRIC`) và ghi đè bằng `SCORING_WEIGHTS` (JSON, kiểm tra đủ 5 mức, không âm), `MIN_SAMPLE`; bảng test: MR nhỏ 1 critical (50) vs MR lớn 20 low (98), clamp 0, false_positive không tính, trần critical.
- 4.2: `process_metrics`: số MR merge, thời gian review TB (giờ, bỏ MR chưa ai review), kích thước MR TB, số vòng review TB, build success rate (%, chỉ tính pipeline success/failed; canceled/skipped không tính).
- 4.3: `aggregate(period_type, period_start)`: kỳ tính theo REPORT_TZ, xoá rồi ghi lại toàn bộ dòng của kỳ (idempotent, không còn dòng cũ). Chỉ tính review `done` (bỏ superseded), bỏ user inactive (bot). avg_score có trọng số LOC, penalty/density theo trọng số của rubric từng review, finding false_positive không tính. Team tính theo thành viên tại thời điểm review/merge. Scheduler: tuần trước lúc 00:30 thứ Hai, tháng trước lúc 00:30 ngày 1.
- 4.4: review MR mới xong → finding critical/high `open` của các review trước mà fingerprint không còn → `fixed`. `fix_rate` (0..1) = tỉ lệ fingerprint critical/high (gộp mọi review của MR) không còn trong review mới nhất; thêm cột `fix_rate` vào 2 bảng metrics bằng migration (08 có, 03 thiếu).
- 4.5: quality_index theo 08 (0.5 điểm + 0.2 mật độ + 0.15 build + 0.15 fix rate); thành phần thiếu (không có pipeline / không có lỗi nặng để sửa) bị bỏ và chia lại trọng số thay vì tính 0; NULL khi reviews < MIN_SAMPLE. `compare_user`/`compare_team`: kỳ này, kỳ trước, delta các chỉ số chính và quality index trung bình của team(s) cho dashboard/báo cáo.
- 4.6: `codepulse metrics recompute --from --to`: chấm lại điểm review (done + superseded) từ finding hiện tại (sau dispute được chấp nhận hoặc đổi SCORING_WEIGHTS) rồi tổng hợp lại mọi tuần/tháng giao với khoảng ngày.
